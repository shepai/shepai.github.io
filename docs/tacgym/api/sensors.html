Sensors¶

Readouts (what an input is computed from), sensor hardware (the MuJoCo model mounted on a robot) and the tools that extract, inspect and attach sensor models.

Readouts¶

.. py:module:: tactip_mujoco_gym.sensors.base

Sensor readouts: the base class, mounts, and the registry.

::

   A *readout* turns simulator state into one observation input ("tactile", "vision", ...). It
   is separate from the sensor *hardware* (the MuJoCo bodies mounted on the robot, see
   sensors/models.py), so the same hardware can be read in several ways (TacTip markers, the
   camera inside the TacTip) and your own readout can be added without touching any env.

   Life cycle, driven by the environment (every hook gets the env, so `env.model`, `env.data`,
   `env.sensor_mounts` and the env's constants are all available):

       bind(env)               once, after the model is compiled: look up ids. Raise
                               SensorUnavailable(reason) if this model can't support the readout
                               (e.g. no marker sites); the env only complains if it is selected.
       calibrate(env, data)    record a rest / reference state (the sensor in free space)
       on_select(env, active)  the input was switched on or off (obs_modes)
       reset(env)              start of every episode, after the scene and robot are placed
       physics_step(env)       after every physics step, only while active and if substeps=True
       env_step(env)           after the physics of every env step
       observe(env)            -> np.ndarray, the observation (called once per env step)
       flatten(value)          how the value goes into the flat ("flat" obs_format) vector
       space(value)            the gymnasium space for the value (default: from its dtype)
       close()                 release renderers etc.

   Register a readout so environments and config files can name it:

       from tactip_mujoco_gym.sensors import Sensor, register_sensor

       @register_sensor("wrist_force")
       class WristForce(Sensor):
           key = "force"                       # default observation key
           def __init__(self, scale=10.0):
               self.scale = scale              # store constructor args under the same name
           def bind(self, env): ...
           def observe(self, env): ...

       env = gym.make("TacArm-peg", sensors={"force": "wrist_force"}, obs_modes=["force"])

   Readouts can also be named as "package.module:ClassName", or registered by an installed
   package through the "tactip_mujoco_gym.sensors" entry-point group.

.. py:module:: tactip_mujoco_gym.sensors.taxels

Event-based readout of the touch-sensor grids (“taxels”, tx_* sensors) that assets/scripts/add_events.py lays over the objects and surfaces of a scene.

::

   A taxel emits an event when its force has changed by at least `threshold` newtons since the
   last event on that taxel (or since reset); the reference level is then set to the current
   force, like a neuromorphic sensor. A steady load produces no events.

   While the input is off and every MuJoCo sensor in the model is a taxel, MuJoCo's sensor
   evaluation is switched off entirely (thousands of touch sensors are a big part of the step
   cost: ~3.4x faster physics in the peg scene).

.. py:class:: TaxelEvents(prefix=None, threshold=None, clip=5.0) :module: tactip_mujoco_gym.sensors.taxels

Bases: :py:class:~tactip_mujoco_gym.sensors.base.Sensor

   threshold  force change (N) that fires an event (default: env.EVENT_THRESHOLD, 0.02)
   clip       counts are clipped to +-clip (default 5)

Hardware¶

.. py:module:: tactip_mujoco_gym.sensors.models

Sensor hardware: the MuJoCo model of the sensor that is mounted on the robot.

::

   Every robot takes `sensor_xml=` (a registered name, a path to a standalone MJCF file, or an
   MjSpec). The file holds just the sensor, with its root body first in <worldbody>:

       <mujoco>
         <asset> ... meshes / materials the sensor uses ... </asset>
         <worldbody>
           <body name="my_sensor"> ... </body>
         </worldbody>
         <tendon> / <equality> / <contact> ... anything between its parts ...
       </mujoco>

   It is attached with a name prefix per mount (FL_, left_, ...; see sensor_tools.attach_sensor),
   turned so its tip points the way the original TacTip's did and moved so the tips coincide.
   The tip is found, in order of preference, from:
       1. a site named "sensor_tip" in the file: its position is the tip, its z axis points out
          of the sensing surface   <site name="sensor_tip" pos="0 0 0.03" zaxis="0 0 1"/>
       2. TacTip-style marker sites (s_c*): a dome is fitted to them
   so a sensor without markers needs the "sensor_tip" site.

       register_sensor_model("my_gelsight", "path/to/gelsight.xml")
       gym.make("TacArm-peg", sensor_xml="my_gelsight")

   "tactip" is the default: assets/sensor/tactip.xml if present. Otherwise the TacTip is
   extracted from assets/tactip_arm.xml, written to that file (if it loads back into the same
   model; delete the file to extract again after changing the sensor in tactip_arm.xml), and
   read from there from then on. `python -m tactip_mujoco_gym.sensor_tools extract ...` writes
   it by hand.

.. py:module:: tactip_mujoco_gym.sensor_tools

Reuse one TacTip model on any robot: extract it once, attach as many prefixed copies as needed.

::

   Why not <include> it several times? <include> pastes the XML text, so every copy has the same
   names (core, pin0_slide, s_c0, ...) and MuJoCo refuses duplicates. Copying the file to
   sensor1/2/3 by hand works, but every equality, tendon and exclude has to be renamed in step.
   MuJoCo's model editing API (MjSpec, MuJoCo >= 3.2) does the renaming for you: attaching a
   body subtree with a prefix renames every body, joint, geom, site, camera, equality, tendon and
   the references between them (FL_core, FL_pin0_slide, FL_s_c0, ...).

   1. Extract the sensor from your arm scene into a standalone file (once):

          python -m tactip_mujoco_gym.sensor_tools extract \
              src/tactip_mujoco_gym/assets/tactip_arm.xml \
              --out src/tactip_mujoco_gym/assets/sensor/tactip.xml

      The sensor is found from its marker sites (s_c*): everything attached to the arm link
      that carries them (link06) is kept - mount, skin, pins, cameras you choose to keep - plus
      the equality constraints and tendons between those parts and the meshes / materials they
      use. The link's own joint and arm geometry are dropped; what is left of it becomes the
      sensor's root body, "tactip". `--body NAME` keeps just one body's subtree instead.
      `python -m tactip_mujoco_gym.sensor_tools tree <scene>` shows where the markers are.

   2. Attach copies in Python:

          spec = mujoco.MjSpec.from_file("go2.xml")
          for leg in ("FL", "FR", "RL", "RR"):
              attach_sensor(spec, spec.body(f"{leg}_calf"), "tactip.xml", prefix=f"{leg}_",
                            tip_at=[0, 0, -0.235], axis_to=[0, 0, -1])   # tip there, pointing down
          model = spec.compile()

      or in XML (MuJoCo >= 3.2), without Python:

          <asset> <model name="tactip" file="sensor/tactip.xml"/> </asset>
          ...
          <body name="FL_calf" ...>
            <attach model="tactip" body="tactip" prefix="FL_"/>
          </body>

      Python is the more flexible route: attach_sensor also points the sensor where you want,
      can stiffen it, and stops it colliding with the link it is mounted on.

.. py:function:: attach_sensor(spec, parent, sensor, prefix, pos=(0, 0, 0), quat=None, axis=None, axis_to=None, tip_at=None, stiffness_scale=1.0, exclude_parent=True) :module: tactip_mujoco_gym.sensor_tools

Attach a prefixed copy of a standalone sensor to body parent of spec.

::

       pos              where the sensor's root body origin goes, in the parent's frame
       quat             its orientation in the parent's frame, or
       axis_to          a direction in the parent's frame for the sensor tip to point along
                        (the tip axis is measured from the markers unless `axis` is given)
       tip_at           with axis_to: put the tip of the sensor at this point (parent frame)
                        instead of placing the root body at `pos`
       stiffness_scale  multiplies stiffness, damping and armature of the sensor's joints and
                        tendons. Scaling all three keeps the natural frequency (so the time
                        step it needs) and the damping ratio unchanged, but carries
                        stiffness_scale x the load at the same deflection: a skin tuned for a
                        few newtons of finger pressure saturates under a robot's weight.
       exclude_parent   no contacts between the sensor and the link it is mounted on

   Returns the attached root body. Its elements are all named prefix + original name.
