TacTip gym environment

TacTip-gym is a reinforcement learning environment designed for training and evaluating agents using vision-based tactile sensing with the TacTip sensor. It extends standard RL frameworks such as OpenAI Gym / Gymnasium to support tactile perception tasks in robotics.

The gym contains four tasks built on one shared robot arm: edge following, peg pushing, shape insertion and incline pushing. Each task tests a different part of contact-rich manipulation, and they share the same arm, controller and Gym interface, so a method can be compared across all of them.

Every task can be run in two observation modes. In privileged mode the policy sees the true state of the scene (where the object is, where the goal is). In tactile mode it only sees the TacTip markers and its own arm, which is the setting a real robot would face. Training in privileged mode first is a quick way to check that a task, reward and controller work before moving to the harder tactile version.

Contents

What is TacTip?

The TacTip is a biomimetic optical tactile sensor that uses a gel-like surface and internal markers tracked by a camera to measure deformation. This allows robots to "feel" contact, edges, texture, and shear forces in a way similar to human touch.

Key Features

  • Gym-style API for reinforcement learning compatibility
  • Simulated tactile observations based on TacTip sensor physics
  • Switch between privileged state and tactile-only observations with one argument
  • A smooth Cartesian controller: no drift, no IK jumps, and the fingertip moves at the speed it is asked to
  • Peg, shape and edge episodes start with the sensor already touching the object
  • Rewards that pay for progress, so agents learn to finish the task rather than hover near it
  • Randomised starts, shapes and surface friction, so policies cannot memorise a single scene
  • Useful for sim-to-real tactile robotics research

Typical Use Cases

  • Edge and surface following with tactile feedback
  • Object manipulation using touch perception
  • Learning contact-rich policies for soft robotics
  • Comparing state-based and tactile-based control strategies
  • Learning to cope with hidden physical properties such as friction

Environment Structure

All environments follow the standard Gym interface: 


import gymnasium as gym
import tactip_mujoco_gym                            # registers the TacArm-* environments

env = gym.make("TacArm-peg")                        # privileged observations (default)
obs, info = env.reset()
action = policy(obs)
obs, reward, terminated, truncated, info = env.step(action)

Why TacTip-gym?

Traditional RL environments rely on visual or state-based inputs. TacTip-gym introduces high-dimensional tactile observations, enabling research into:

  • Contact-driven learning
  • Robust manipulation under uncertainty
  • Sensorimotor learning from touch

This project is ideal for researchers working in robotics, reinforcement learning, and tactile perception who want to explore how machines can learn from touch.

The Environments at a Glance

Every environment inherits from a common RobotArmEnv class, which itself builds on TactileGymEnv. The base class owns the arm, the controller, the observation modes and the reset logic. Each task then supplies its own scene, task state, reward and termination rule.

Observation Modes

Both modes start with the same short proprioception block, because a real robot always knows where its own arm is:

  • Fingertip position (3)
  • Commanded fingertip position minus measured fingertip position, divided by 1 cm (3). When the fingertip is pressed against something it lags behind the command, so this acts as a rough force sense.
  • The smoothed velocity command the arm is currently following (2, or 3 for edge following)

What follows depends on the mode:

Mode After the proprioception block Use it for
Privileged (default) The task state: object position, vector to the goal, object velocity, whether the sensor is touching, and so on (listed per environment below) Checking that a task, reward and controller can be learned at all, and as an upper bound for tactile policies
Tactile Marker displacement from the untouched sensor (3 per marker, in mm), then the change in each marker since the previous step (3 per marker, in mm) Learning from touch alone: the object and the goal are never given directly

The mode can be chosen when the environment is made, or switched afterwards. Either way the observation space is rebuilt from a real observation, so its size can never get out of step with what step() returns: 

env = gym.make("TacArm-peg", privileged=False)     # tactile from the start (use this for training)
env.unwrapped.set_privileged(True)                 # or switch later; rebuilds env.observation_space

The marker reading comes from get_nodes(), which returns every s_c* marker site in the sensor's own frame. The untouched marker positions are recorded once when the environment is built, with the arm held in free space, and every tactile observation is measured against them. Values are reported in millimetres so they are already of order one.

Tactile events from the tx_* taxels on the objects can still be added in either mode. They are appended as one value per taxel: the signed number of events since the previous step. While events are switched off, MuJoCo's sensor evaluation is disabled entirely, because computing thousands of unused touch sensors was a large part of the simulation cost. 

env.unwrapped.set_event(True)      # append taxel events to the observation
events = env.unwrapped.get_events()   # raw events: [taxel_index, polarity, time]

Shared Robot and Controller

The robot arm is simulated in MuJoCo. The learning agent controls the movement of the fingertip rather than each individual joint. The fingertip is represented by an end-effector site called ee_site.

How Does the Agent Ask the Arm to Move?

Every action component lies between -1 and 1 and is read as a fingertip velocity. Before it is used, it passes through a light low-pass filter: 

velocity_cmd = 0.6 * velocity_cmd + 0.4 * action
target      += velocity_cmd * 0.005                # 5 mm per step at full speed (0.25 m/s)

The filter matters more than it looks. Early in training the agent's actions are mostly exploration noise, and unfiltered noise jerks the fingertip back and forth. In the peg task that knocks the cylinder over almost every time, so the agent never sees a successful push to learn from. With the filter, a roughly correct policy plus the same noise went from 0 to 12 successes out of 16 attempts. The filtered velocity is part of the observation, so the agent always knows what the arm is currently doing.

The action size depends on the task:

  • Peg and ShapeInsertion: 2 dimensions (x and y). The fingertip height is held 1.5 cm above the platform, low on the object, so it slides rather than tips.
  • Incline: 2 dimensions in the ramp's own coordinates: along the slope and sideways. The height is set from the ramp surface.
  • Edge following: 3 dimensions. x and y move at up to 4 mm per step; z moves at up to 1.5 mm per step, so the contact depth can be controlled finely.

How Does the Robot Actually Move?

  1. The agent produces an action. It is clipped to -1 to 1 and smoothed into a velocity command.
  2. The target position moves. The velocity command is added to the commanded fingertip position, which is kept inside the task's workspace.
  3. The leash is applied. The command may not run more than 1 cm ahead of the measured fingertip. When the fingertip is blocked (pushing against something heavy, or pressing into a surface) the command stops there instead of running away. It is never pulled back towards the measured fingertip, so a slightly sagging arm cannot drag it downwards.
  4. Inverse kinematics solves the arm. A few iterations of damped least-squares IK turn the commanded fingertip position into joint angles for joints 1 to 6.
  5. Feed-forward is added. The arm's joint servos are stiff spring-dampers. On their own they lag a tenth of a second behind any motion and sag under gravity, so the joint targets get a velocity term and a gravity term added.
  6. MuJoCo advances the simulation. The joint targets are blended in over 20 physics steps (20 ms) and the robot moves.

Inverse Kinematics

Inverse kinematics, or IK, solves the opposite problem to normal robot motion calculations. Instead of starting with joint angles and asking where the fingertip will be, we start with a desired fingertip position and ask which joint positions will place the fingertip there.

The solver uses the Jacobian of ee_site and takes damped least-squares steps towards the target position, while holding the sensor's orientation fixed: 

target_orientation = [1.0, 0.0, 0.0, 0.0]
error  = [target_pos - tip_pos,  0.3 * orientation_error]
dq     = J.T @ inv(J @ J.T + 0.0005 * I) @ error

Two details keep the arm smooth. First, the solver runs on a separate copy of the simulation data, so it never disturbs the physics. Second, each step starts from the previous joint command, not from the measured joint angles. The measured joints sag a little under gravity and lag during motion, and starting from them made the solution creep and occasionally jump between different arm configurations. Starting from the last command, the arm stays in one configuration and the solver usually converges in one or two iterations.

Why the controller works this way

The first version of the gym passed small fingertip steps to a general-purpose IK solver that started from the measured joints and stopped once it was within 1 mm of the target. The steps were smaller than that tolerance, so the solver usually returned the current (sagging) joint angles, and the commanded position was then reset to wherever the fingertip had sagged to. The result was an arm that slowly drifted downwards whatever the agent asked for. Measured on a test arm, the fingertip sank about 4 cm in 2 seconds, and asking it to move at full speed gave almost the same motion as asking it to stay still. No reward design can fix that, so the controller was rebuilt first.

The new controller holds the fingertip still with zero drift, moves at exactly the commanded speed, tracks the command to within half a millimetre and keeps the sensor's orientation within about 0.1 degrees.

The Reset Sequence

Every reset follows the same order, so the arm never sweeps an object out of place at the start of an episode:

  1. The simulation is reset.
  2. The task randomises its scene (object position, shape, block rotation, friction and so on) and places the objects.
  3. The arm is teleported to an IK solution for the task's start pose, just clear of the object, and held still for 100 physics steps to settle. Teleporting avoids swinging the arm across the scene.
  4. For edge following, peg and shape insertion, the fingertip creeps towards the object (about 1 mm every 10 ms) until the sensor touches it, then stops. If a light object is nudged away and contact is lost, it tries again with finer steps.

The result is that these episodes start with the sensor touching the object, which is essential in tactile mode: without vision, the agent has no other way to find the object. In our tests 100% of resets began in contact, with the object at rest and upright.

The incline is different by design. The fingertip is placed somewhere on the lower half of the ramp and the ball is dropped further up, so the episode begins with the ball rolling down towards the fingertip.

How Rewards Are Built

All four tasks share the same reward recipe. Each step's reward is roughly between -1 and 1, and is mostly made of progress: how much closer the task got to being done during that step. 

progress = clip((previous_distance - current_distance) / 0.005, -1, 1)

Dividing by 5 mm (one full-speed step) means progress is 1 when the object moves towards the goal as fast as the arm can push it, and negative when it moves away. Alongside it are a few small "closeness" terms that give direction early on, all built from the same smooth function: 

closeness(d, sigma) = 1 - tanh(|d| / sigma)    # 1 at d = 0, 0.24 at d = sigma, about 0 beyond 3 sigma

Finishing and failing are handled at the end of the episode:

  • Success: +100 and the episode ends.
  • Unrecoverable failure (object tipped over, wrong hole, ball off the ramp, edge lost): -10 and the episode ends.

Every term depends only on what the environment can see right now. There are no hidden stage counters, so the value function always has the information it needs.

Why progress rather than closeness?

An earlier version paid mainly for closeness: being near the goal, and having the fingertip behind the object. In the peg task, a policy that did nothing at all scored 103 over an episode, because it collected that closeness reward for all 250 steps. A noisy attempt at pushing tipped the cylinder over most of the time and scored 16 to 56. The agent correctly learned that sitting still was the best thing to do, and its success rate stayed at about 5%. Paying for progress fixes this. Doing nothing now earns very little, and a successful push is clearly the best outcome.

Environment 1: Edge Following

This was the first task in the gym. The arm starts touching the top edge of a rectangular block and has to follow that edge all the way round, anticlockwise when seen from above.

The block is randomly rotated at the beginning of each episode, and the starting point is chosen at random on one of the four top edges (at least 1.5 cm from a corner). The fingertip is placed above that point and lowered until it touches the block. The height at which contact is made is recorded, and the agent is rewarded for keeping that contact depth. Because the block is rotated, the robot has to learn a general way of following an edge rather than memorising one path.

Measuring Position on the Edge

The top of the block is treated as a loop of four line segments, 0.6 m in total. For any fingertip position the environment finds the closest point on that loop and works out:

  • Arc length: how far round the loop that point is
  • Sideways error: the distance from the edge, positive outside the block and negative inside
  • Tangent: the anticlockwise direction of the edge at that point

The change in arc length each step is the progress along the edge. It handles the wrap-around at the start of the loop, and the running total tells the environment when a full lap is complete.

Observation and Action

In privileged mode the observation has 22 dimensions: proprioception (9) followed by

  • Block centre relative to the fingertip (2)
  • Sine and cosine of the block's rotation (2)
  • Nearest edge point relative to the fingertip (2)
  • Edge direction to follow (2)
  • Sideways error, height error from the recorded contact depth, distance to the next corner, fraction of the lap completed, and whether the sensor is touching (5)

In tactile mode the agent has to read the edge from the sensor: the markers show where the edge crosses the dome and which side of it the block is on. The action has 3 dimensions, so the agent controls contact depth as well as direction.

Reward and Termination

on_edge  = closeness(sideways_error, 0.005)      # 5 mm
depth    = closeness(height_error, 0.003)        # 3 mm
touching = 1 if the sensor touches the block else 0
progress = clip(arc_length_change / 0.004, -1, 1)

reward = (
    0.10 * on_edge
    + 0.05 * touching
    + 0.05 * depth
    + 0.80 * on_edge * touching * progress    # progress only counts on the edge and in contact
)
  • Success: +100 after one full lap.
  • Fail: -10 if the fingertip ends up more than 2.5 cm from the edge, lifts more than 2 cm off the block, or slips more than 1.5 cm down its side.

Going the wrong way round gives negative progress, so the direction is part of the task.

Environment 2: Peg

The Task

An upright cylinder sits on a platform. There is a hole in the platform, and the arm has to push the cylinder across the surface until it drops into the hole. The cylinder is 4 cm wide, and the hole is 6 cm wide, which leaves 1 cm of clearance on each side. Making the hole tighter makes the task harder.

The cylinder starts at a random position 8 to 12 cm from the hole and up to 2 cm to either side of it. The fingertip starts touching the cylinder on the side facing away from the hole, at 1.5 cm above the platform. Pushing that low keeps the cylinder sliding rather than tipping.

The Scene

MuJoCo has no way to cut a hole out of a solid shape, so the platform is built from four box slabs arranged around a gap. The cylinder is a free body with its own freejoint, so it can slide, roll and tip over as it would in reality.

Observation and Action

In privileged mode the observation has 20 dimensions: proprioception (8) followed by

  • The cylinder position (3)
  • The horizontal vector from the cylinder to the hole (2)
  • The horizontal vector from the cylinder to the fingertip (2)
  • How far the cylinder is tilted (2)
  • The cylinder's horizontal velocity (2)
  • Whether the sensor is touching it (1)

In tactile mode none of the cylinder values are given. The hole never moves, so the policy can learn where it is, but it has to feel where the cylinder is relative to its fingertip. The action is a 2-dimensional fingertip movement (x and y).

Reward and Termination

push_point = cylinder - direction_to_hole * (cylinder_radius + tip_radius)

reward = (
    0.1 * closeness(tip - push_point, 0.02)    # fingertip behind the cylinder
    + 0.2 * closeness(goal_dist, 0.08)          # cylinder near the hole
    + 0.7 * progress(goal_dist)                 # cylinder moved towards the hole this step
)
  • Success: +100 when the cylinder is over the hole and has dropped by 1.5 cm.
  • Fail: -10 if the cylinder tips more than about 30 degrees, is lying on its side, or goes off the platform anywhere other than the hole.

Tipping is not counted while the cylinder is over the hole, because it tilts as it drops in.

The Push Point

The closeness term guides the fingertip towards the push point: the spot on the far side of the cylinder from the hole. A fingertip placed there and moved towards the hole pushes the cylinder straight in. It is recomputed every step, so if the cylinder drifts sideways the push point moves with it and the agent learns to correct.

Environment 3: ShapeInsertion

The Task

ShapeInsertion extends the peg task. The platform now has four holes (a circle, a square, a rectangle and a triangle), and each episode the arm is given one of the four shapes. It starts touching the shape and must push it to the matching hole. In tactile mode the agent is not told which shape it has, so it has to identify the shape by touch before it knows which hole to aim for.

Hidden Shapes

All four shapes exist in the MuJoCo scene, but only one is visible and solid in any given episode. The other three are hidden by:

  • Making them fully transparent
  • Turning their collisions off
  • Parking them out of the way and putting them back in place after every step. Setting gravity compensation at runtime is not enough: MuJoCo only applies it if the model was built with it.

This lets the scene be built once and reused. Picking a different shape only changes a few model properties at reset time.

Generated Holes

The holes need exact geometry, so a short Python script generates the scene XML. A shared configuration file stores the shape sizes, the hole positions and the clearance (4 mm per side), and both the XML generator and the environment read from it, so the numbers cannot drift apart. Round and triangular holes are cut from thin strips of box geometry.

Randomisation and Curriculum

  • Which shape is shown (and therefore which hole is the goal)
  • The start position on the platform
  • The starting rotation (yaw) of the shape

Two arguments control how hard the task is: 

env = gym.make("TacArm-shape",
               spawn_yaw=0.1,            # starting rotation range, +/- radians
               spawn_toward_hole=0.0)    # 0 = start in the middle, 1 = start in line with the right hole
env.reset(options={"shape": "square"})   # fix a single shape

By default shapes start within 0.1 radians of the hole's orientation, which fits every hole without re-orienting. Setting spawn_yaw to pi means the agent has to rotate the shape by pushing it off-centre, which is much harder with a single point of contact. spawn_toward_hole moves the start position towards the correct hole, turning the task into a straight push. A sensible order is straight pushes first, then central starts, then larger starting rotations.

Observation and Action

In privileged mode the observation has 25 dimensions: proprioception (8) followed by

  • Shape position (3)
  • Sine and cosine of (symmetry order × yaw), and the yaw error (3)
  • Vector from the shape to its target hole (2)
  • Vector from the shape to the fingertip (2)
  • Shape velocity (2)
  • Whether the sensor is touching it (1)
  • One-hot shape identity (4)

The action is a 2-dimensional fingertip movement (x and y).

Symmetry-Aware Orientation

Some shapes already fit through their hole at more than one angle. The yaw error accounts for this by wrapping the angle by the shape's rotational symmetry: 

period = 2 * pi / symmetry_order
yaw_error = (yaw + period / 2) % period - period / 2
  • Circle: any rotation fits, so the yaw error is always zero
  • Square: repeats every 90 degrees
  • Rectangle: repeats every 180 degrees
  • Triangle: repeats every 120 degrees

Without this, the agent would be penalised for rotations that already fit.

Reward and Termination

near = clip(1 - goal_dist / 0.10, 0, 1)    # 0 more than 10 cm from the hole, 1 at the hole

reward = (
    0.10 * closeness(tip - push_point, 0.02)
    + 0.15 * closeness(goal_dist, 0.12)
    + 0.60 * progress(goal_dist)
    + 0.15 * near * closeness(yaw_error, 0.15)    # orientation only matters near the hole
)
  • Success: +100 when part of the shape is at least 8 mm below the plate surface within 3 cm of the correct hole.
  • Fail: -10 if it goes into the wrong hole or off the edge, tips over more than 5 cm from its hole, or ends up lying on the plate.

Success is measured from the shape's lowest point rather than its centre. With a 2 cm thick plate and only 4 mm of clearance, a pushed shape tips forward as it reaches the hole and wedges in at an angle instead of dropping straight through. Counting only a fully dropped shape made the task almost impossible. A shape lying flat on the plate never has any part below the surface, so it cannot be mistaken for an insertion.

Orientation is still enforced by the physics. A square turned by 45 degrees cannot go into the square hole. A circle could go into the square hole, which is why going into any hole other than the target counts as a failure.

Environment 4: Incline

The Task

The fingertip starts somewhere on the lower half of a 15 degree ramp, and a ball is dropped further up. The ball rolls down towards the fingertip. The agent has to intercept it without letting it slip past, then push it back up to the top. Pushing a ball uphill with a single rounded fingertip is unstable, so the agent has to keep correcting sideways to stay directly below the ball.

The twist is that the friction of the ramp changes every episode. The same push produces very different behaviour depending on the surface:

  • Low friction: the ball rolls freely, so it rolls back down as soon as the fingertip stops pushing. The agent must keep pushing continuously.
  • High friction: the ball holds its place on the slope, so the agent can push in short bursts.

Randomised Friction

At the start of each episode a single friction level f between 0 and 1 is picked and mapped to both friction coefficients of the ramp: 

sliding = 0.05 * (1.0 / 0.05) ** f      # log-interpolated, 0.05 to 1.0
rolling = 0.008 * f                      # linear, 0 to 0.008
  • Sliding friction from 0.05 to 1.0, interpolated on a log scale
  • Rolling friction from 0 to 0.008, interpolated linearly

Rolling friction is what makes a ball's behaviour on a slope depend on the surface. With sliding friction alone, the ball would roll back down at nearly the same rate whatever the surface. The ramp and ball therefore use MuJoCo's 6-dimensional contact model, which includes rolling friction. The ball itself has very low friction, because MuJoCo uses the larger of the two touching surfaces' values, so the ramp's friction dominates. The ramp's colour also gets darker as friction rises (visual only).

The Ramp Frame

The environment reads the ramp's position and tilt from the model. It works out the up-slope direction and the surface normal itself, so changing the ramp angle in the XML does not break the Python code.

Observation and Action

The action is 2-dimensional: movement along the slope, and movement sideways, both in the ramp's own coordinates. After the same smoothing as the other tasks, each component moves a commanded fingertip position in slope coordinates: 

cmd_s = clip(cmd_s + velocity_cmd[0] * 0.005, -0.06, L - 0.03)   # along the slope
cmd_y = clip(cmd_y + velocity_cmd[1] * 0.005, -0.06, 0.06)       # sideways

The fingertip height is computed from the ramp surface so it stays level with the ball's centre, which stops it pushing over the top of the ball.

In privileged mode the observation has 23 dimensions: proprioception (8) followed by

  • Fingertip position in slope coordinates: distance up the slope (as a fraction of its length), sideways, height (3)
  • Ball position in slope coordinates (3)
  • Fingertip offset from the ball, along the slope and sideways (2)
  • Ball velocity in slope coordinates (3)
  • Ball spin, multiplied by its radius (3)
  • Whether the sensor is touching the ball (1)

An optional extra value gives the policy the true friction level, making the observation 24 dimensions. It is off by default: 

env = gym.make("TacArm-hill", observe_friction=True)

Hidden Friction

With friction hidden, the policy has to work it out from how the ball responds to being pushed. In privileged mode the ball's velocity and spin make this possible, and in our tests the policy learned the task without frame stacking. In tactile mode the ball is only felt once it touches the sensor, so frame stacking or a recurrent policy may help there.

Reward and Termination

reward = (
    0.15 * closeness(tip - point_just_below_ball, 0.03)   # stay behind the ball
    + 0.25 * ball_height                                  # distance up the ramp, 0 to 1
    + 0.60 * progress(ball_height)                        # + pushing it up, - letting it roll down
)

At the start of the episode the ball is rolling downhill, so the progress term is negative until it is stopped. This pushes the agent to move up and meet the ball early, rather than waiting for it at the bottom.

  • Success: +100 when the ball gets within 4 cm of the top.
  • Fail: -10 if the ball rolls off the bottom, goes more than 10 cm sideways, or pops off the surface.

Evaluation

The friction can be fixed for evaluation, so a trained policy can be tested at each end of the range: 

env.reset(options={"friction": 0.0})   # slippery
env.reset(options={"friction": 1.0})   # grippy

Training

The examples folder contains RL_BASE.py, which wraps Stable-Baselines3. Each task has a short script that calls it: 

from RL_BASE import run, evaluate, visualise

if __name__ == "__main__":          # required: each environment runs in its own process
    run("TacArm-peg", "peg_v2", "peg_v2", 3_000_000, privileged=True)    # or privileged=False
    evaluate("TacArm-peg", "peg_v2", n_episodes=50)                      # success rate, no viewer
    visualise("TacArm-peg", "peg_v2")                                    # MuJoCo viewer

run() creates one environment per process, normalises observations and rewards with VecNormalize, logs to logs/<name>/progress.csv, saves a checkpoint every 500,000 steps and records a short video at every 20% of training. At the end it saves three files:

  • <name>.zip: the policy
  • <name>_vecnormalize.pkl: the observation statistics. The policy was trained on normalised observations and behaves almost randomly without them, so these are saved after training and loaded by evaluate(), visualise() and the training videos.
  • <name>.json: the environment name, its arguments and the algorithm, so the same environment is rebuilt for evaluation.

Checking an Environment Before Training

check_envs.py runs a quick set of checks on each task in a few minutes: whether the arm drifts or lags, whether resets start in contact, and whether a simple hand-written controller using the privileged state can solve the task. If the hand-written controller cannot solve a task, a learned policy will not either, so this is worth running after any change to the scene or the sensor.

Using the Environments

Each environment can be trained with any algorithm that supports Gymnasium. The tasks are designed to be tackled in roughly this order of difficulty:

  1. Edge following: learn to stay in contact with a surface using touch.
  2. Peg: learn to push an object to a goal without tipping it.
  3. Incline: stop a moving object, then push against gravity with a hidden friction level.
  4. ShapeInsertion: a changing goal, tight clearances and optional re-orientation.

Each task can then be repeated in tactile mode, where the agent has to do the same thing by touch alone.

Adding Your Own Task

A new task needs a MuJoCo scene file and a class that inherits from RobotArmEnv. The base class handles the controller, the observation modes, the marker readout, success and failure bonuses, and episode length. The task fills in a few hooks:

  • _setup_task(): look up the bodies and joints it needs, once
  • _reset_task(options): place the objects and the arm (helpers place the arm by IK and creep into contact)
  • _privileged_obs(): the task state for privileged mode
  • _reward(): the per-step reward
  • _status(): return "success", "fail" or None

Tasks with a different action layout, such as the incline's slope coordinates, can also override _apply_action(). The observation space is sized automatically, so there is no observation dimension to keep in sync by hand.
