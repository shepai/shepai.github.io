TacTip gym environment

TacTip-gym is a reinforcement learning environment designed for training and evaluating agents using vision-based tactile sensing with the TacTip sensor. It extends standard RL frameworks such as OpenAI Gym / Gymnasium to support tactile perception tasks in robotics.

The gym now contains four tasks built on one shared robot arm: edge following, peg pushing, shape insertion and incline pushing. Each task tests a different part of contact-rich manipulation, and they share the same arm, controller and Gym interface, so a method can be compared across all of them.

Contents

What is TacTip?

The TacTip is a biomimetic optical tactile sensor that uses a gel-like surface and internal markers tracked by a camera to measure deformation. This allows robots to "feel" contact, edges, texture, and shear forces in a way similar to human touch.

Key Features

  • Gym-style API for reinforcement learning compatibility
  • Simulated tactile observations based on TacTip sensor physics
  • Useful for sim-to-real tactile robotics research
  • Designed for benchmarking tactile perception and control tasks
  • Four tasks of increasing difficulty that share one arm and one control scheme
  • Randomised starts, shapes and surface friction, so policies cannot memorise a single scene

Typical Use Cases

  • Edge and surface following with tactile feedback
  • Object manipulation using touch perception
  • Learning contact-rich policies for soft robotics
  • Comparing vision vs tactile-based control strategies
  • Learning to cope with hidden physical properties such as friction

Environment Structure

All environments follow the standard Gym interface: 


obs, info = env.reset()
action = policy(obs)
obs, reward, terminated, truncated, info = env.step(action)

Why TacTip-gym?

Traditional RL environments rely on visual or state-based inputs. TacTip-gym introduces high-dimensional tactile observations, enabling research into:

  • Contact-driven learning
  • Robust manipulation under uncertainty
  • Sensorimotor learning from touch

This project is ideal for researchers working in robotics, reinforcement learning, and tactile perception who want to explore how machines can learn from touch.

The Environments at a Glance

Every environment inherits from a common RobotArmEnv class, which itself builds on TactileGymEnv. The base class owns the arm, the controller and the reset logic. Each task then supplies its own scene, observation, reward and termination rule.

Shared Robot and Controller

The robot arm is simulated in MuJoCo and is controlled through a Gym-style reinforcement learning environment. The learning agent, PPO, controls the movement of the fingertip rather than directly controlling each individual joint. The fingertip is represented by an end-effector site called ee_site.

How Does PPO Ask the Arm to Move?

PPO produces an action which is treated as a movement of the robot's fingertip, not as joint angles. In the edge-following and peg environments the action has 3 dimensions, and it is scaled and added to the fingertip's current position: 

self.current_position += action * 0.5

The third action component is disabled: 

action[2] = 0

This stops the agent moving the fingertip along the Z axis and reduces the problem to pushing in the horizontal plane. The incline environment is different: the ramp is tilted, so the fingertip has to climb with the slope. It uses a 2-dimensional action instead (see below).

How Does the Robot Actually Move?

PPO does not directly control the six arm joints. It requests a new fingertip position, and the environment uses inverse kinematics to work out which joint positions are needed to reach it.

  1. PPO produces an action. The action describes the requested movement of the fingertip.
  2. The target position changes. The action is scaled and added to the current fingertip position.
  3. Inverse kinematics solves the arm. The requested fingertip position is passed to the IK solver.
  4. Joint targets are calculated. The IK solver determines suitable positions for joints 1 to 6.
  5. MuJoCo advances the simulation. The joint targets are applied and the simulated robot moves.

Inverse Kinematics

Inverse kinematics, or IK, solves the opposite problem to normal robot motion calculations. Instead of starting with joint angles and asking where the fingertip will be, we start with a desired fingertip position and ask which joint positions will place the fingertip there.

The environment uses the ee_site as the target and keeps the end-effector orientation fixed: 

fixed_orientation = [1.0, 0.0, 0.0, 0.0]

The Reset Sequence

Each environment resets in the same order, so the arm can never sweep an object out of place at the start of an episode:

  1. The base class resets the simulation and moves the arm to a default pose.
  2. The task randomises its scene (object position, shape, friction and so on).
  3. The arm is moved to the task's start pose.
  4. The object is placed, then the simulation runs for 50 steps with the arm held still so everything settles.
  5. The reward's "previous distance" values are stored, so the first step is not given a false reward.

The PPO Control Loop

Learning in every environment follows the same repeating loop:

  1. Observe: the environment provides the current observation to PPO.
  2. Choose an action: PPO produces a fingertip movement.
  3. Move: the action changes the desired fingertip position.
  4. Solve: inverse kinematics converts the position into joint targets.
  5. Simulate: MuJoCo advances the robot.
  6. Measure: the environment calculates the new observation and reward.
  7. Learn: PPO uses the experience to improve its future decisions.

A Note on Progress Rewards

The pushing tasks below all reward the change in distance to the goal rather than the distance itself. A reward based on raw distance pays the agent for simply sitting near the goal, so a policy can learn to hover without ever pushing. A reward based on change only pays for real progress, and it goes negative if the agent pushes the object away. 

reward = scale * (previous_distance - current_distance)

Environment 1: Edge Following

This was the first task in the gym, and it tests whether the arm can follow the edge of a rectangular block using its fingertip.

The environment randomly rotates the block at the beginning of an episode and selects a starting point on one of the four top edges. This means the robot needs to learn a general strategy for following an edge rather than memorising one fixed position.

What Does the Robot Observe?

The observation has a dimension of 213. The environment obtains it using get_nodes() and then flattens the result into a single array. 

observation = self.get_nodes().flatten()

The 213 values are the positions of the optical markers of the TacTip. They have already been put into an embedded space to simplify the input, and the coordinates are local in 3D space relative to one another.

How Is Reward Enforced?

A good action should help the fingertip stay close to the edge and make progress along it. The reward is made from three ideas:

  • How close the fingertip is to the edge.
  • Whether the robot is making progress along the edge.
  • Whether sufficient contact is being maintained.

Distance from the Edge

The environment finds the point on the block that is closest to the fingertip and measures the horizontal distance to it: 

edge_point = self.closest_edge_point(tip)
edge_error = np.linalg.norm(
    tip[:2] - edge_point[:2]
)

The further the fingertip moves away from the edge, the larger the edge_error becomes. This produces a negative reward of -2.0 * edge_error, so staying close to the edge is encouraged.

Progress Along the Edge

The top edges of the block are divided into a sequence of points. The environment keeps track of which point the robot should reach next, and moves on to the next point when the fingertip gets close enough: 

if edge_error < 0.01:
    self.current_target += 1

The change in progress from the previous step is rewarded with: 

delta_progress = progress - self.previous_progress
+5.0 * delta_progress

Contact Penalty

If the measured force is below 0.1, a penalty of 5 is applied. In the current implementation the force is temporarily set to a fixed value of 0.2, and the real contact-force calculation is marked as a future implementation. 

if force < 0.1:
    contact_penalty = 5

Overall Reward

reward = (
    -2.0 * edge_error
    + 5.0 * delta_progress
    - contact_penalty
)

In simple terms, the robot is rewarded for staying close to the edge and making progress along it.

Environment 2: Peg

The Task

An upright cylinder sits on a platform. There is a hole in the platform, and the arm has to push the cylinder across the surface until it drops into the hole. The cylinder is 4 cm wide, and the hole is 6 cm wide, which leaves 1 cm of clearance on each side. Making the hole tighter makes the task harder.

The cylinder starts at a random position just behind the hole, so the agent has to learn to approach it from the correct side rather than repeat one fixed motion.

The Scene

MuJoCo has no way to cut a hole out of a solid shape, so the platform is built from four box slabs arranged around a gap. The cylinder is a free body with its own freejoint, so it can slide, roll and tip over as it would in reality.

Observation and Action

The observation has 8 dimensions:

  • The fingertip position (3)
  • The cylinder position (3)
  • The horizontal vector from the cylinder to the hole (2)

The action is the same 3-dimensional fingertip movement as before, with Z locked.

Reward and Termination

The cylinder must stay upright. If it tips more than about 30 degrees from vertical, or ends up off the platform without being over the hole, the episode ends immediately with a penalty. Otherwise the reward is built from progress: 

reward = (
    10.0 * (previous_goal_dist - goal_dist)   # push the cylinder towards the hole
    + 1.0 * (previous_tip_dist - tip_dist)    # weak: reach the push point
    - 0.01                                    # time penalty
)
  • Success: +100 when the cylinder drops into the hole.
  • Fall: -50 and the episode ends.

Success is checked before falling. A cylinder tilts as it drops through the hole, and that must not be counted as a fall.

The Push Point

The approach term guides the fingertip towards the push point: the spot on the far side of the cylinder from the hole, at the cylinder's mid-height. A fingertip placed there and moved towards the hole pushes the cylinder in. Pushing near the top of the cylinder is the main cause of tipping, which is why the Z axis is locked at mid-height.

Environment 3: ShapeInsertion

The Task

ShapeInsertion extends the peg task. The platform now has four holes (a circle, a square, a rectangle and a triangle), and each episode the arm is given one of the four shapes. It must push that shape to the matching hole and rotate it into the right orientation, because a shape that is the wrong way round will not fit through.

Hidden Shapes

All four shapes exist in the MuJoCo scene, but only one is visible and solid in any given episode. The other three are hidden by:

  • Making them fully transparent
  • Turning their collisions off
  • Parking them out of the way with gravity compensated, so they do not fall forever

This lets the scene be built once and reused. Picking a different shape only changes a few model properties at reset time.

Generated Holes

The holes need exact geometry, so a short Python script generates the scene XML. A shared configuration file stores the shape sizes, the hole positions and the clearance (4 mm per side), and both the XML generator and the environment read from it, so the numbers cannot drift apart. Round and triangular holes are cut from thin strips of box geometry.

Randomisation

  • Which shape is shown (and therefore which hole is the goal)
  • The start position on the platform
  • The starting rotation (yaw) of the shape

Observation and Action

The observation has 15 dimensions:

  • Fingertip position (3)
  • Shape position (3)
  • Sine and cosine of the shape's yaw (2)
  • Vector from the shape to its target hole (2)
  • Yaw error (1)
  • One-hot shape identity (4)

The shape identity and the target vector are essential. Without them the task could not be solved from the observation, because the same shape position needs a different push for each shape. The action is the 3-dimensional fingertip movement with Z locked.

Symmetry-Aware Orientation

Some shapes already fit through their hole at more than one angle. The yaw error accounts for this by wrapping the angle by the shape's rotational symmetry:

  • Circle: any rotation fits, so the yaw error is always zero
  • Square: repeats every 90 degrees
  • Rectangle: repeats every 180 degrees
  • Triangle: repeats every 120 degrees

Without this, the agent would be penalised for rotations that already fit.

Reward and Termination

reward = (
    10.0 * (previous_goal_dist - goal_dist)   # push towards the correct hole
    + 1.0 * (previous_yaw_err - yaw_err)      # rotate towards the hole's orientation
    + 1.0 * (previous_tip_dist - tip_dist)    # weak: reach the push point
    - 0.01                                    # time penalty
)
  • Success: +100 when the shape drops through the correct hole.
  • Fail: -50 if it drops through the wrong hole or off the edge, or tips over away from the target hole.

Orientation is enforced by the physics itself. A square turned by 45 degrees simply cannot drop through the square hole. A circle could drop through the square hole, which is why a drop through any hole other than the target counts as a failure.

Curriculum

A single-point pusher, random rotations and four different targets together make a hard exploration problem. The environment supports a curriculum: 

env.spawn_yaw = 0.0                       # start with no rotation needed
env.reset(options={"shape": "square"})    # fix a single shape

A sensible order is to train with a single shape and no rotation, then add random rotation, then add all four shapes.

Environment 4: Incline

The Task

A ball starts near the bottom of a 15 degree ramp, and the arm has to push it up to the top. The twist is that the friction of the ramp changes every episode. The same push produces very different behaviour depending on the surface:

  • Low friction: the ball rolls freely, so it rolls back down as soon as the fingertip stops pushing. The agent must keep pushing continuously.
  • High friction: the ball holds its place on the slope, so the agent can push in short bursts.

Randomised Friction

At the start of each episode a single friction level between 0 and 1 is picked and mapped to both friction coefficients of the ramp:

  • Sliding friction from 0.05 to 1.0, interpolated on a log scale
  • Rolling friction from 0 to 0.008, interpolated linearly

Rolling friction is what makes a ball's behaviour on a slope depend on the surface. With sliding friction alone, the ball would roll back down at nearly the same rate whatever the surface. The ramp and ball therefore use MuJoCo's 6-dimensional contact model, which includes rolling friction. The ball itself has very low friction, because MuJoCo uses the larger of the two touching surfaces' values, so the ramp's friction dominates.

The Ramp Frame

The environment reads the ramp's position and tilt from the model. It works out the up-slope direction and the surface normal itself, so changing the ramp angle in the XML does not break the Python code.

Observation and Action

The action is 2-dimensional: movement along the slope, and movement sideways. The fingertip height is computed from the ramp surface so it stays level with the ball's centre, which stops it pushing over the top of the ball. Each environment step runs 10 physics steps with the joint targets held.

The observation has 12 dimensions:

  • Fingertip position (3)
  • Ball position (3)
  • Ball velocity (3)
  • Ball progress along the ramp, as a fraction of its length (1)
  • Fingertip offset from the ball, along the slope and sideways (2)

An optional 13th value gives the policy the true friction level. This is useful for checking that the task can be learned at all, but it is turned off by default.

Hidden Friction

With friction hidden, the policy has to work it out from how the ball responds to being pushed. The ball velocity in the observation is what makes this possible. A policy that only sees one frame at a time cannot easily compare the ball's motion across steps, so the hidden version of the task is best trained with frame stacking or a recurrent policy.

Reward and Termination

reward = (
    30.0 * (ball_progress - previous_ball_progress)   # up the slope is good, rolling back is bad
    + 1.0 * (previous_tip_dist - tip_dist)            # weak: stay behind the ball
    - 0.01                                            # time penalty
)
  • Success: +100 when the ball gets within 4 cm of the top.
  • Fail: -50 if the ball rolls off the bottom, falls off the side, or pops off the surface.

Evaluation

The friction can be fixed for evaluation, so a trained policy can be tested at each end of the range: 

env.reset(options={"friction": 0.0})   # slippery
env.reset(options={"friction": 1.0})   # grippy

Using the Environments

Each environment is a Python class that inherits from RobotArmEnv, and can be trained with any algorithm that supports Gymnasium. The tasks are designed to be tackled in roughly this order of difficulty:

  1. Edge following: learn to stay in contact with a surface using touch.
  2. Peg: learn to push an object to a goal without tipping it.
  3. ShapeInsertion: add orientation control and a changing goal.
  4. Incline: adapt to a physical property that the agent cannot see directly.

Adding Your Own Task

A new task needs three things: a MuJoCo scene file, a class that inherits from RobotArmEnv, and four methods. The reset method places the arm and the objects, _get_obs() builds the observation, _reward() returns the reward for the step, and _done() says whether the episode has ended.
